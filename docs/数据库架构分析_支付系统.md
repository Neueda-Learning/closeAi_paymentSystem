# 支付处理系统 — 数据库表设计分析报告

> 资深系统架构师视角 | 分析日期：2026-07-27

---

## 一、现有表结构全景

当前系统只有 **3 张表**：

| 表名 | 行数估算 | 核心职责 |
|------|---------|---------|
| `payments` | 主表 | 支付单核心字段 + 当前状态 |
| `status_history` | N×payments | 每次状态转换的审计追踪 |
| `idempotency_keys` | ≈payments | 幂等键 → payment_id 映射 |

### payments 表字段清单

```
id                  VARCHAR(36)   PK          — UUID
idempotency_key     VARCHAR(64)   NOT NULL    — 幂等键（冗余存储）
source_account      VARCHAR(50)   NOT NULL    — 源账号（裸字符串，无外键）
destination_account VARCHAR(50)   NOT NULL    — 目标账号（裸字符串，无外键）
amount              DECIMAL(15,2) NOT NULL    — 金额
currency            VARCHAR(3)    NOT NULL    — 货币码（裸字符串，无外键）
description         TEXT                       — 描述
status              VARCHAR(20)   NOT NULL    — 当前状态
error_code          VARCHAR(50)               — 最后错误码
version             INT           NOT NULL    — 乐观锁版本
created_at          TIMESTAMP     NOT NULL    — 创建时间
updated_at          TIMESTAMP     NOT NULL    — 更新时间
```

### status_history 表字段清单

```
id          BIGINT        PK AUTO_INCREMENT
payment_id  VARCHAR(36)   NOT NULL FK→payments
from_status VARCHAR(20)               — 前一状态
to_status   VARCHAR(20)   NOT NULL    — 新状态
changed_at  TIMESTAMP     NOT NULL    — 变更时间
reason      TEXT                       — 变更原因
error_code  VARCHAR(50)               — 错误码
```

### idempotency_keys 表字段清单

```
key_record  VARCHAR(64)   PK          — 幂等键值
payment_id  VARCHAR(36)   NOT NULL    — 关联支付 ID（无外键约束）
created_at  TIMESTAMP     NOT NULL    — 创建时间
```

## 二、三张表是否太少？—— 核心判断

**是的，3 张表对于"满足规范要求 + 接入 AI 风控"来说明显不够。**

但判断不是简单看数量——而是看**每张表的职责是否自洽、是否存在概念混叠、是否有不可弥补的功能缺口**。以下是逐维度剖析。

---

## 三、现有设计的 6 个架构问题

### 问题 1：`payments` 表职责过重 — 状态快照 + 业务实体 + 错误信息 三位一体

`payments` 表同时承担了：
- **业务实体**（谁付谁、多少、什么币种）
- **状态快照**（当前 status + error_code）
- **关联索引**（idempotency_key 冗余存储）

这导致：

1. **error_code 只记录最后一次错误** — 一笔支付可能经历"验证失败→FAILED→重试→SENT→网络失败→FAILED"，两次失败各有不同 error_code，但 payments 表只保留最后一次。历史错误码只能去 status_history 查——这意味着**获取"当前错误"必须从 status_history 反推而非直接读 payments**，违反直觉。

2. **idempotency_key 在 payments 和 idempotency_keys 双写** — 同一个信息存了两遍。payments.idempotency_key 和 idempotency_keys.key_record + payment_id 完全可以只存后者。当前设计让 payments 表多了一个不该属于它的字段。

3. **更新频繁** — 每次状态变更都 UPDATE payments（status/error_code/version/updated_at），对于金融审计场景，**主表应该是低频写入的**，高频变动的状态应独立存储。

### 问题 2：`source_account` / `destination_account` 是裸字符串 — 没有账户实体

这是**最严重的架构缺陷**。规范附录 C 明确要求：

> "Accounts must exist in the system"

当前 `source_account` 和 `destination_account` 只是 VARCHAR(50) 字符串，意味着：
- 无法校验账户是否真实存在（只能校验格式 `ACC-\d{3,10}`）
- 无法检查余额是否充足 → `INSUFFICIENT_FUNDS` 错误码是死代码
- 无法追踪某个账户的所有支付（只能靠 LIKE 模糊搜索）
- 无法实现"冻结账户""账户限额"等任何高级功能
- 无法为 AI 风控提供账户交易历史（"同一账户最近 10 分钟交易 5 笔"这类速度规则无法高效计算）

**在真实支付系统中，账户是一等公民，不是支付单的一个字段。**

### 问题 3：`currency` 是硬编码白名单 — 没有货币配置实体

`ValidationService` 用 `Set.of("USD", "EUR", "GBP", "CNY")` 硬编码支持币种。这意味着：
- 添加新币种需要改代码、重新部署（而不是改数据库配置）
- 无法存储币种的小数精度规则（JPY 是 0 位小数、BHD 是 3 位）
- 无法做多币种汇率转换（规范高级功能第 7 项）
- 无法区分"系统支持"和"网关支持"（某些币种只对特定网关可用）

### 问题 4：`status_history` 缺少触发者字段 — 审计链断裂

规范明确问："Who/what triggered the status change?" 当前 `status_history` 没有 `triggered_by` 字段：

- 状态变更可能是：API 调用者、模拟网关自动触发、系统定时任务、AI 风控拦截
- 没有这个字段，审计日志无法回答"这笔 FAILED 是谁/什么导致的"
- 对合规和事后调查来说是致命缺失

### 问题 5：`idempotency_keys` 无外键约束 — 数据一致性隐患

`idempotency_keys.payment_id` 没有 FK 指向 `payments.id`（这是之前修复外键循环依赖时移除的）。代价是：
- 支付记录删除后会留孤儿幂等记录
- 幂等键可能指向一个不存在的 payment_id
- 没有数据库层面的一致性保障，全靠应用层逻辑

### 问题 6：缺少 AI 风控结果存储 — 无法回溯风险评估

你选了 AI 异常检测作为扩展方向，但当前没有任何表存储风险评估结果。这意味着：
- AI Agent 的风险分数、触发的规则、决策依据无处持久化
- 无法事后回溯"这笔支付为什么被 AI 拦截"
- 无法做风险模型的效果评估（拦截了多少、误报了多少）
- 前端风险面板无数据源

## 四、建议新增的 4 张表（含完整 DDL）

### 建议 1：accounts 表（P0 — 规范强制要求）

这是**最优先**的补充。没有账户实体，3 个规范要求（账户存在性、余额检查、INSUFFICIENT_FUNDS）永远无法满足。

```sql
CREATE TABLE IF NOT EXISTS accounts (
    account_id      VARCHAR(50)   PRIMARY KEY,          -- 格式 ACC-XXX
    account_name    VARCHAR(100)  NOT NULL,              -- 账户持有人名称
    balance         DECIMAL(15,2) NOT NULL DEFAULT 0.00, -- 当前余额
    currency        VARCHAR(3)    NOT NULL,              -- 账户币种
    status          VARCHAR(20)   NOT NULL DEFAULT 'ACTIVE', -- ACTIVE / FROZEN / CLOSED
    daily_limit     DECIMAL(15,2) NULL,                  -- 每日支付限额（可选）
    created_at      TIMESTAMP     NOT NULL DEFAULT CURRENT_TIMESTAMP,
    updated_at      TIMESTAMP     NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
    CONSTRAINT chk_balance_non_negative CHECK (balance >= 0)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;

-- Seed data: 预置几个账户用于开发和演示
INSERT INTO accounts (account_id, account_name, balance, currency, daily_limit) VALUES
('ACC-001', 'Alice Wang', 50000.00, 'CNY', 100000.00),
('ACC-002', 'Bob Zhang', 12000.50, 'USD', 50000.00),
('ACC-003', 'Charlie Li', 8000.00, 'EUR', 20000.00),
('ACC-004', 'Diana Chen', 300000.00, 'GBP', 500000.00),
('ACC-005', 'Eve Liu', 500.00, 'CNY', 5000.00);       -- 低余额账户（触发 INSUFFICIENT_FUNDS）

CREATE INDEX idx_accounts_status ON accounts (status);
CREATE INDEX idx_accounts_currency ON accounts (currency);
```

**联动改动**：

| 改动点 | 说明 |
|--------|------|
| `payments.source_account` / `destination_account` | 加 FK 指向 accounts.account_id |
| `ValidationService.validateOnTransition` | 加账户存在性查询 + 余额充足性检查 |
| ErrorCode `INSUFFICIENT_FUNDS` | 激活：源账户余额 < 支付金额时抛出 |
| ErrorCode `INVALID_ACCOUNT` | 激活：账户不在 accounts 表中时抛出 |
| AI 风控的速度规则 | 可查询 accounts 关联的近期支付历史 |

### 建议 2：currencies 表（P1 — 提升扩展性）

把货币白名单从硬编码改为数据驱动。

```sql
CREATE TABLE IF NOT EXISTS currencies (
    code            VARCHAR(3)    PRIMARY KEY,           -- ISO 4217
    name            VARCHAR(50)   NOT NULL,              -- 全名
    decimal_places  INT           NOT NULL DEFAULT 2,     -- 小数精度（JPY=0, BHD=3）
    is_supported    BOOLEAN       NOT NULL DEFAULT TRUE,  -- 是否在系统中可用
    symbol          VARCHAR(5)    NOT NULL,               -- $ / € / £ / ¥
    created_at      TIMESTAMP     NOT NULL DEFAULT CURRENT_TIMESTAMP
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;

INSERT INTO currencies (code, name, decimal_places, is_supported, symbol) VALUES

('EUR', 'Euro', 2, TRUE, '€'),
('GBP', 'British Pound Sterling', 2, TRUE, '£'),
('CNY', 'Chinese Yuan', 2, TRUE, '¥'),
('JPY', 'Japanese Yen', 0, FALSE, '¥'),    -- 不支持但有汇率数据
('BHD', 'Bahraini Dinar', 3, FALSE, 'BD'); -- 不支持但有汇率数据

-- 未来多币种兑换时加此表
-- CREATE TABLE IF NOT EXISTS exchange_rates (
--     from_currency VARCHAR(3), to_currency VARCHAR(3),
--     rate DECIMAL(10,6), effective_date DATE,
--     PRIMARY KEY (from_currency, to_currency, effective_date)

```

**联动改动**：

| 改动点 | 说明 |
|--------|------|
| `ValidationService.SUPPORTED_CURRENCIES` | 改为从 currencies 表动态加载 |
| `payments.currency` | 加 FK 指向 currencies.code |
| 金额小数校验 | 从 currencies.decimal_places 动态读取精度规则 |
| DTO `@Digits(10,2)` | 改为动态校验（JPY 整数、BHD 3 位） |

### 建议 3：risk_assessments 表（P1 — AI 风控必需）

为 AI 异常检测模块提供持久化存储。

```sql
CREATE TABLE IF NOT EXISTS risk_assessments (
    id              BIGINT        AUTO_INCREMENT PRIMARY KEY,
    payment_id      VARCHAR(36)   NOT NULL,
    risk_score      INT           NOT NULL,               -- 0-100 分
    risk_level      VARCHAR(10)   NOT NULL,               -- LOW / MEDIUM / HIGH / CRITICAL
    decision        VARCHAR(20)   NOT NULL,               -- APPROVE / REVIEW / BLOCK
    rules_triggered TEXT          NULL,                    -- JSON: 触发的规则列表
    assessment_source VARCHAR(20) NOT NULL DEFAULT 'RULE_ENGINE', -- RULE_ENGINE / STAT_MODEL / LLM
    details         TEXT          NULL,                    -- JSON: 风险评估详细上下文
    assessed_at     TIMESTAMP     NOT NULL DEFAULT CURRENT_TIMESTAMP,
    CONSTRAINT fk_risk_payment FOREIGN KEY (payment_id) REFERENCES payments(id)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;

CREATE INDEX idx_risk_payment_id ON risk_assessments (payment_id);
CREATE INDEX idx_risk_level ON risk_assessments (risk_level);
CREATE INDEX idx_risk_decision ON risk_assessments (decision);
```

**联动改动**：

| 改动点 | 说明 |
|--------|------|
| `PaymentServiceImpl.processValidate` | AI hook 位置：调用 riskAssessmentService.assess(payment) → 写 risk_assessments → BLOCK 时转 FAILED |
| ErrorCode `RISK_BLOCKED` | 激活：AI 决策为 BLOCK 时抛出 |
| 前端风险面板 | 数据源：GET /api/payments/{id}/risk → 返回 risk_assessments 记录 |
| `PaymentResponse` | 加 riskScore/riskLevel/riskDecision 字段 |

### 建议 4：audit_logs 表（P2 — 审计完整性增强）

替代/补充 `status_history`，记录**所有操作**（不仅是状态变更），且包含触发者信息。

```sql
CREATE TABLE IF NOT EXISTS audit_logs (
    id              BIGINT        AUTO_INCREMENT PRIMARY KEY,
    entity_type     VARCHAR(20)   NOT NULL,               -- PAYMENT / ACCOUNT / RISK_ASSESSMENT
    entity_id       VARCHAR(36)   NOT NULL,               -- 实体 ID
    action          VARCHAR(30)   NOT NULL,               -- CREATE / VALIDATE / SEND / FAIL / RETRY / BLOCK / FREEZE_ACCOUNT ...
    triggered_by    VARCHAR(50)   NOT NULL,               -- VALIDATE_API / SIMULATED_GATEWAY / SYSTEM / RISK_ENGINE / USER_ADMIN
    old_value       TEXT          NULL,                    -- 变更前状态（JSON）
    new_value       TEXT          NULL,                    -- 变更后状态（JSON）
    result          VARCHAR(10)   NOT NULL DEFAULT 'SUCCESS', -- SUCCESS / FAILURE
    error_code      VARCHAR(50)   NULL,
    ip_address      VARCHAR(45)   NULL,                   -- 未来扩展：请求来源 IP
    created_at      TIMESTAMP     NOT NULL DEFAULT CURRENT_TIMESTAMP
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;

CREATE INDEX idx_audit_entity ON audit_logs (entity_type, entity_id);
CREATE INDEX idx_audit_action ON audit_logs (action);
CREATE INDEX idx_audit_created_at ON audit_logs (created_at);
```

**与 status_history 的关系**：

status_history 仍保留（它是支付状态变更的专用窄表，查询效率高），audit_logs 是**全系统通用审计表**（覆盖所有实体和操作）。两者互补：
- `GET /payments/{id}/history` → 查 status_history（快速、专一）
- `GET /audit?entity_id=XXX` → 查 audit_logs（全面、含触发者）

## 五、现有 3 张表的改进建议

不仅需要新增表，现有表也需要调整：

### payments 表改进

| 改动 | 原因 |
|------|------|
| 移除 `idempotency_key` 字段 | 与 idempotency_keys 表重复存储， payments 表不应承载幂等关联 |
| `source_account` 加 FK → accounts | 数据一致性保障 |
| `destination_account` 加 FK → accounts | 数据一致性保障 |
| `currency` 加 FK → currencies | 数据一致性保障 |
| `error_code` 加注释说明 | 明确"这是最后一次错误码，完整历史查 status_history" |

改进后的 payments 表：

```sql
CREATE TABLE IF NOT EXISTS payments (
    id                  VARCHAR(36)   PRIMARY KEY,
    source_account      VARCHAR(50)   NOT NULL,
    destination_account VARCHAR(50)   NOT NULL,
    amount              DECIMAL(15,2) NOT NULL,
    currency            VARCHAR(3)    NOT NULL,
    description         TEXT,
    status              VARCHAR(20)   NOT NULL DEFAULT 'CREATED',
    error_code          VARCHAR(50)   COMMENT 'Last error code; full history in status_history',
    version             INT           NOT NULL DEFAULT 0,
    created_at          TIMESTAMP     NOT NULL DEFAULT CURRENT_TIMESTAMP,
    updated_at          TIMESTAMP     NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
    CONSTRAINT fk_payment_source FOREIGN KEY (source_account) REFERENCES accounts(account_id),
    CONSTRAINT fk_payment_dest FOREIGN KEY (destination_account) REFERENCES accounts(account_id),
    CONSTRAINT fk_payment_currency FOREIGN KEY (currency) REFERENCES currencies(code)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;
```

### status_history 表改进

| 改动 | 原因 |
|------|------|
| 加 `triggered_by` 字段 | 规范要求"Who/what triggered the status change" |

```sql
-- 新增字段
ALTER TABLE status_history ADD COLUMN triggered_by VARCHAR(50) NOT NULL DEFAULT 'API'
    AFTER error_code;
-- 触发者可选值：API / SIMULATED_GATEWAY / SYSTEM / RISK_ENGINE / RETRY_API / ADMIN
```

### idempotency_keys 表改进

| 改动 | 原因 |
|------|------|
| `payment_id` 加回 FK（条件：先插 payment 再插 idempotency） | 数据一致性保障 |
| 加 `expires_at` 字段 | 幂等键不应永久有效（Stripe 24h 过期，控制存储膨胀） |

```sql
CREATE TABLE IF NOT EXISTS idempotency_keys (
    key_record  VARCHAR(64)   PRIMARY KEY,
    payment_id  VARCHAR(36)   NOT NULL,
    created_at  TIMESTAMP     NOT NULL DEFAULT CURRENT_TIMESTAMP,
    expires_at  TIMESTAMP     NOT NULL DEFAULT (CURRENT_TIMESTAMP + INTERVAL 24 HOUR),
    CONSTRAINT fk_idempotency_payment FOREIGN KEY (payment_id) REFERENCES payments(id)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;
```

## 七、7 张表 vs 3 张表 — 对比论证

| 维度 | 3 张表 | 7 张表 |
|------|--------|--------|
| **规范合规** | 账户存在性❌ / 余额检查❌ / 触发者❌ | 全部✅ |
| **AI 风控** | 无存储→无法回溯 | risk_assessments 完整记录 |
| **错误码覆盖** | 3 个死码 | 全部 10+1 活码 |
| **扩展性** | 加币种改代码 | 加币种改数据库 |
| **数据一致性** | 3 个裸字符串字段 | 3 个 FK 保障 |
| **审计完整性** | 缺触发者 | status_history + audit_logs 双层 |
| **幂等键存储** | 永久有效+双写 | 24h 过期+单写 |
| **演示说服力** | "INSUFFICIENT_FUNDS 是死码" | "看，ACC-005 余额只有 ¥500，支付 ¥5000 触发了余额不足拦截" |
| **查询效率** | 账户相关查询只能 LIKE | 直接 JOIN accounts |
| **开发复杂度** | 低（简单但有缺口） | 中（多表但更健壮） |

## 九、对"3 张表是否太少"的最终回答

**3 张表对于"能跑通支付生命周期"的最小可行系统是够的**——这正是规范所说的"STAY AGILE, start with minimal fields"。但如果目标是：

1. ✅ 满足规范所有验证要求（账户存在性、余额检查）
2. ✅ 让全部 10 个错误码可触发（不是死码）
3. ✅ 接入 AI 风控模块（需要风险评估结果持久化）
4. ✅ 完整审计链（触发者记录）
5. ✅ 数据驱动配置（币种白名单不硬编码）
6. ✅ 向生产级系统演进（账户实体、外键约束、幂等键过期）

**那 3 张表绝对不够，至少需要 7 张。**

核心判断：**payments / status_history / idempotency_keys 三张表是"骨架"，accounts / currencies / risk_assessments / audit_logs 四张表是"肌肉"。骨架让系统能站住，肌肉让系统能战斗。**
